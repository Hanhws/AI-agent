## 11. 10/4 (3) — 크롬 확장의 ‘읽기’ (내보내기 없이 웹 대화 읽기)

## 12. 10/4 (4) — 대화 찾기 · 다시 켜면 새 코드

**대화 찾기** — 대화가 90개를 넘으니 왼쪽 목록에서 찾기 힘들어서, 가닥 창 왼쪽 위에 찾는 칸을 넣었어요. 프로젝트를 가리지 않고 모든 대화에서 찾아요. 프로토타입에는 없는 것이고, 가닥 창에만 있어요(`backend/web/app.js` · `app.css`, 길은 `GET /chats/search?q=`).

- 차례: 대화 제목 · 프로젝트 이름 · 쓴 곳(ChatGPT · Cursor · Claude Code …)이 맞는 대화가 먼저, 그다음 글이 맞는 대화. 그 안에서는 최근에 쓴 대화가 위
- 한 줄의 모양: 제목과 날짜 / 프로젝트 · 쓴 곳 / 맞은 글의 둘레(두 줄까지). 누르면 그 대화의 그 턴으로 가요
- 노선도 카드 안의 ‘지난 대화에서 찾기’(7-9)는 그대로예요(그 프로젝트 안의 턴을 찾음)

- [ ] **문구**: 칸의 안내 “대화 찾기” · “찾은 대화 n개” · “찾는 중이에요…” · “찾은 대화가 없어요.”
- [ ] **자리와 모양**: 심볼 아래, 목록 위. 칸은 카드 안의 찾기 칸과 같은 모양(`.qin`)을 썼어요
- [ ] 두 찾기(왼쪽 위 = 모든 대화, 카드 안 = 이 프로젝트의 턴)를 하나로 합칠지
- [ ] **사용 기록**: ‘대화 찾기를 썼다’는 적지 않아요(`usage_schema.py`의 `ui.what`에 낱말이 없어서). 넣을지
- [ ] 확인 뒤 `docs/schema.md` 3번 API 표에 `GET /chats/search?q=` 추가 (제안)

**다시 켜면 새 코드** — 코드를 고친 뒤 가닥 앱을 껐다 켜도, 터미널 등에서 먼저 켜 둔 예전 가닥이 뒤에 남아 있으면 앱이 거기에 그대로 붙어서 새 기능이 안 보였어요(크롬 확장이 보낸 대화가 안 들어오던 까닭). 이제 켤 때 코드를 견줘서, 다르면 예전 가닥을 끄고 새로 켜요(`backend/launch.py` · `/health`의 `code`). 화면이나 문구는 바뀌지 않았어요.

**아직 확인하지 못한 것**: 사람이 직접 칸에 치는 것(크롬에서 스크립트로 쳐서 확인), 한글을 조합하는 중의 동작, 대화가 수천 개일 때의 빠르기.

## 13. 10/4 (5) — 왜 만들었나, 모은 사용 기록으로 무엇을 어떻게 고치나

10/3 밤부터 더한 기능이 여럿이라, **각각 어떤 불편에서 나왔는지**와 **서버에 모으는 사용 기록이 가닥을 고치는 데 어떻게 쓰이는지**를 한곳에 적어요. 발표에서 “왜 이렇게 만들었나”를 말할 때도 쓸 수 있어요.

### 13-1. 더한 기능과 만든 까닭

| 기능 | 어떤 불편 · 필요에서 나왔나 | 그래서 한 것 | 자세히 |
|---|---|---|---|
| 켜면 알아서 읽고 정리 | 입구마다 명령을 쳐서 붙여야 했어요. 쓰는 사람이 설정부터 해야 하면 쓰지 않아요 | 켜면 이 PC의 기록을 찾아 읽고, 보는 대화부터 정리해 보여 줌 | 6번 |

| 다시 켜면 새 코드 | 앱을 껐다 켜도 뒤에 남은 예전 가닥이 계속 돌아서 새 기능이 안 보였어요 | 켤 때 코드를 견줘, 다르면 예전 것을 끄고 바꿔 켬 | 12번 |

### 13-2. 사용 기록으로 무엇을 알 수 있나 — 이유와 방법

**서버로 가는 것** — 동의한 사람의 기록 아홉 종류(`open` · `chat` · `classify` · `check` · `item` · `ui` · `import` · `connect` · `stop`)이고, 값은 숫자 · 참거짓 · 정해 둔 낱말뿐이에요(10번의 표, 전부는 `backend/usage_schema.py`). 같이 가는 것은 무작위 설치 번호 · 가닥 버전 · 기록의 차례 번호 · 날짜(시각 없음)예요. 대화 글 · 제목 · 파일 이름 · 프로젝트 이름 · 찾는 말 · 계정은 가지 않아요. 크롬 확장이 읽은 웹 대화도 각자 PC의 가닥까지만 가요.

아래는 만든 예시예요. 실제로도 이 모양 그대로 가요.

```
open     {"via": "app", "os": "mac", "engine": "claude_cli", "projects": 6, "chats": 31, "turns": 240, "chats_claude_code": 20, "chats_chatgpt": 8, "chats_claude": 3}
chat     {"chat": "3f9a1c0b7d2e", "site": "chatgpt", "turns": 18, "side": 4, "deep": 1, "decided": 3, "multi": 2, "segments": 3, "files": 1, "in_project": 4}
item     {"kind": "missing", "did": "run", "at": "nudge"}
classify {"turns": 8, "done": 8, "seconds": 11}
```

풀어 읽으면: “Mac 앱에서 Claude 구독으로 쓰는 사람이고, 대화 31개 중 20개가 Claude Code다. ChatGPT의 18턴짜리 대화에 곁길이 4턴, 정한 것이 3개 있었다. ‘빠진 요청’ 한마디를 카드에서 실행했다. 8턴을 정리하는 데 11초 걸렸다.”

**왜 글 없이도 쓸모가 있나** — 가닥이 하는 일은 ‘읽기 → 정리 → 한마디 → 사용자가 실행’으로 이어지는 줄이에요. 대화 글이 없어도 이 줄의 **어디에서 얼마나 빠지는지**는 수로 보여요. 무엇을 먼저 고칠지는 그것으로 정할 수 있어요.

| 기록 | 알 수 있는 것 | 그래서 정하는 것 |
|---|---|---|
| `item` (만듦 → 보임 → 실행 · 나중에 · 닫음) | 한마디 종류별 실행률. 예: ‘빠진 요청’은 절반이 실행되는데 ‘이어 가기’는 거의 닫힘 | 안 쓰이는 한마디는 도는 조건 · 문구를 고치거나 뺌. 잘 쓰이는 것은 앞으로 |
| `chat` (턴 수 · 곁길 수 · 구간 수 · 같은 프로젝트의 대화 수) | 사용 유형. 프로젝트로 나눠 쓰는지, 한 창에 몰아 쓰는지, 매번 새 창을 여는지 | 주제 나누기와 이어 가기 요약 중 무엇에 힘을 줄지. 설문의 “U1이 압도적”을 실제 쓰임으로 다시 확인 |
| `open` (입구별 대화 수, 켠 날) | 어느 입구를 실제로 쓰는지, 며칠이나 계속 쓰는지 | 입구의 우선순위, 실제로 쓰이는지 |
| `classify` · `check` · `stop` | 정리 호출 수와 걸린 시간, 2단의 걸음 · 쓴 도구, 한도나 엔진 문제로 멈춘 횟수 | 호출 한도 · 묶는 턴 수 · 2단이 도는 조건. 구독 한도를 어디서 쓰는지 |
| `ui` | 어떤 탭 · 버튼이 눌리고 안 눌리는지 | 안 쓰는 화면은 줄이고, 자주 쓰는 것은 앞으로 |
| `import` · `connect` | 불러오기 · 연결이 실패하는 비율 | 어느 입구의 붙이는 과정을 먼저 고칠지 |

**어떻게 쓰나 (방법)**

1. **본다** — 가닥 팀 서버의 통계 화면(주소와 암호는 각자 PC의 `서버-정보.local.md`). 이미 이렇게 묶어 보여 줘요: 설치 수와 날짜별 사용, 입구별 대화 수, 대화의 모양(턴 수 · 같은 프로젝트의 대화 수 · 곁길 · 정함 · 여러 요청 · 파일이 있는 대화의 비율), 한마디 종류별 만듦 → 보임 → 실행 → 나중에 → 닫음, 누른 것, 정리 호출의 시간, 2단의 걸음 · 도구 · 멈춘 까닭.
2. **기준을 미리 정한다** — 숫자를 보고 나서 뜻을 붙이면 원하는 대로 읽게 돼요. 아래는 제안이에요.
   - 한마디 **실행률** = 실행 ÷ 보임 (종류별). 스무 번 넘게 보였는데 20% 아래면 그 종류의 조건 · 문구를 다시 봐요
   - **닫음** ÷ 보임이 절반을 넘으면 잔소리로 보고 조건을 좁혀요
   - 2단이 **한마디를 만든 비율** = 만든 확인 ÷ 돈 확인. 너무 낮으면 1단의 후보가 헛도는 것이고, 구독 한도만 써요
   - 2단의 평균 걸음이 한도(5)에 가깝거나 한도로 끝난 확인이 많으면 한도 · 도구를 다시 봐요
   - 사용 유형: 같은 프로젝트에 대화가 여럿이면 프로젝트 분리형(U1), 41턴이 넘는 대화가 많으면 한 창 몰아쓰기(U2), 1~5턴 대화가 대부분이면 매번 새 창(U3), 곁길이 있는 대화의 비율이 높으면 분기 활용(U4)
3. **고친다** — 프롬프트 문구(`backend/prompts/`), 2단이 도는 조건, 화면.
4. **다시 본다** — 기록마다 가닥 버전이 같이 저장돼서, 고치기 전과 뒤를 나눠 볼 수 있어요. 통계 화면에 버전별 보기는 아직 없어요.

**알 수 없는 것 (한계)**

- **판단이 맞았는지.** ‘닫음’이 틀려서인지 이미 해서인지 구분되지 않아요. 실행률은 맞았는지의 어림일 뿐이에요.
- **왜 틀렸는지.** 글이 없어서 실패한 사례를 들여다볼 수 없어요.
- **지금은 쓰는 사람이 몇 명뿐**이라 비율보다 건수로 읽어야 해요.
- 이 부분은 다른 것으로 채워요: 예시 대화의 정답 라벨로 하는 정확도 평가(`eval/`), 10/11 측정 세션(직접 보고 묻기), 각자 PC에 남는 2단의 판단 기록.

**이 과제에서의 쓸모**

- 발표에서 “한마디 실행률 몇 %, 정리 한 번에 몇 초” 같은 숫자를 근거로 낼 수 있어요.
- 측정 세션(3-4의 A · B)의 전 · 후 비교에 같은 숫자를 써요.
- “사용자 데이터를 어떻게 다뤘나”에 구조로 답할 수 있어요: 모으는 표에 글이 들어갈 칸이 없어요.

**정해 주세요 (제안이고, 아직 넣지 않았어요)**

- [ ] **‘닫음’을 둘로 나누기**: “필요 없어요”와 “이미 했어요”. 가닥의 판단이 맞았는지를 수로 볼 수 있어요. 닫기 버튼이 둘이 되어 화면이 바뀌어요
- [ ] 한마디가 보인 뒤 실행까지 **걸린 시간(초)**
- [ ] ‘대화 찾기’를 쓴 횟수, 크롬 확장을 넣었는지 (11번 · 12번에도 적었어요)
- [ ] 통계 화면에 **버전별 보기**
- [ ] 위 2번의 **기준 숫자**(20% · 절반 · 스무 번)

## 14. 10/4 (6) — 승인한 종류의 자동 실행

README 3-2의 ‘승인한 종류만 자동 실행’을 만들었어요. 지금까지 가닥은 글을 복사해 줄 뿐이었는데, 이제 **사용자가 켠 종류만** 가닥이 직접 보내요. 교수님이 말한 ‘사람이 개입하는 시점’의 설계라서 일정(10/6)보다 먼저 했어요. 쓰는 법은 `docs/usage-guide.md` 5-2.

**어떻게 도나**

1. 사용자가 할 일 목록 맨 아래의 ‘가닥이 알아서 보내는 것’에서 종류를 **켜요**. 한마디를 직접 보내는 창의 ‘앞으로는 알아서’ 칸에서도 켤 수 있어요.
2. 그다음부터, 턴이 끝날 때(요청 외 변경) · 새 대화가 시작될 때(이어 가기) Cursor · Claude Code의 hook이 가닥에 “이어서 보낼 글이 있나요?”를 물어요.
3. 가닥은 켠 종류에 대해서만 답해요. 요청 외 변경은 **2단이 바뀐 곳을 직접 보고 만든 한마디**가 그 턴에 있을 때만, 그 한마디의 ‘원래대로’ 글을 돌려줘요.
4. 보낸 것은 할 일 목록에 ‘가닥이 보냄’으로 남고, 목록 아래에서 종류별로 꺼요.

| 만든 것 | 어디 |
|---|---|
| 보낼지 정하는 곳 | `backend/auto.py` (`/auto` · `/auto/stop` · `/auto/start`) |
| 실제로 보내는 곳 | `cursor-hooks/gadak-hook.py` — Cursor: `followup_message` · `additional_context`, Claude Code: `decision: block` · `additionalContext` |
| Claude Code에 hook 둘 붙이기 · 떼기 | 찾은 곳의 ‘자동 실행 연결 · 끊기’ (`backend/sources/__init__.py`). 사용자가 눌렀을 때만, 있던 설정은 그대로, 고치기 전 파일을 옆에 남김 |
| 화면 | 창의 ‘앞으로는 알아서’ 칸(`shared/ui/nudge.js`), 목록의 ‘가닥이 보냄’과 끄기(`shared/ui/side.js`) |
| 보낸 것의 기록 | `auto_log` 테이블 (각자 PC에만) |

**잘못 보내지 않게 건 것**

- 자동으로 할 수 있는 종류는 코드에 둘로 박혀 있어요(요청 외 변경 · 이어 가기). 나머지 여덟은 켤 수 없어요
- 근거: 2단이 `get_diff`로 바뀐 곳을 보지 않고 낸 결론은 원래 버려요(8번). 가닥이 보내는 것은 그렇게 남은 한마디뿐이에요
- 되풀이 막기: 가닥이 보낸 글로 이어진 턴에는 다시 보내지 않아요. 같은 한마디를 두 번 보내지 않아요
- 가닥이 파일을 직접 고치지 않아요. LLM에게 되돌려 달라고 **요청**만 해요

**확인해 주세요 — 문구 (전부 임시)**

- [ ] 켜는 칸: “앞으로는 알아서”
  - 요청 외 변경: “이런 요청 외 변경은 다음부터 가닥이 바로 되돌려 달라고 보내요. 할 일 목록에서 끌 수 있어요.”
  - 이어 가기: “같은 프로젝트의 새 대화에는 다음부터 가닥이 시작할 때 요약을 넣어요. 할 일 목록에서 끌 수 있어요.”
- [ ] 할 일 목록: 한마디 종류 뒤의 “· 가닥이 보냄”, 묶음 제목 “가닥이 알아서 보내는 것”, 줄마다 “요청 외 변경 · 켜짐 / 꺼짐”과 “켜기” · “끄기”
- [ ] 알림: “다음부터 ‘요청 외 변경’은 가닥이 바로 보내요.” · “켰어요. 가닥이 직접 보내려면 ‘찾은 곳’에서 Claude Code를 연결해 주세요.” · “켰어요. 가닥이 직접 보낼 수 있는 곳은 지금 Claude Code와 Cursor예요.” · “‘요청 외 변경’은 다시 물어보고 보낼게요.”
- [ ] 찾은 곳의 Claude Code 줄: “‘앞으로는 알아서’를 켠 것을 가닥이 직접 보내려면 연결해요. Claude Code 설정에 hook 둘을 더해요” · “가닥이 직접 보낼 수 있어요(자동 실행 연결됨)” · 버튼 “자동 실행 연결” · “자동 실행 끊기” · “연결했어요. 새로 여는 Claude Code 대화부터 가닥이 직접 보낼 수 있어요.”
- [ ] **가닥이 대화에 보내는 글의 머리말**: “[가닥이 대신 보냄] ” + 한마디의 ‘원래대로’ 글. 이 글은 LLM이 읽는 글이에요
- [ ] 새 대화에 넣는 요약: 한마디의 ‘요약 붙이기’와 같은 글(“지난 대화에서 정한 것 / 1. … / 이 결정을 그대로 두고 이어서 진행해 줘.”)
- [ ] 목록에 남는 이어 가기: “지난 대화에서 정한 것 n개를 이 대화에 붙였어요” · “같은 프로젝트의 새 대화라서, 시작할 때 가닥이 넣었어요.”

**정해 주세요 — 디자인 (11장의 ‘미정’ 그대로예요)**

- [ ] **켜는 자리**: 지금은 할 일 목록 맨 아래에 두 종류가 ‘켜짐 · 꺼짐’과 함께 늘 보이고, 한마디를 보내는 창 안에도 칸이 있어요. 처음에는 창 안의 칸만 있었는데 놓치기 쉬워서 목록 아래에 더했어요. 어디가 맞을지
- [ ] **‘가닥이 보냄’을 어떻게 보일지**: 지금은 끝난 일(줄 그은 글)에 글자만 붙어요
- [ ] **이어 가기 요약에 넣을 것**: 지금은 그 프로젝트의 최근 결정 9개를 그대로 넣어요(시작할 때라 LLM이 고를 시간이 없어요). 개수와 고르는 법
- [ ] **기다리는 시간**: 켜 둔 동안 파일이 바뀐 턴이 끝날 때 최대 40초(재 본 한 번은 약 25초). 괜찮은지
- [ ] ‘원래대로’ 글이 어색할 때가 있어요: “‘임계값만 1300으로 변경’ 변경만 남겨 줘”처럼 틀이 ‘변경’을 한 번 더 붙여요(8번의 문구)
- [ ] 사용 기록: 가닥이 보낸 것은 새 칸 없이 `item {did: run, at: auto}`로 적어요. 승인을 켰는지는 적지 않아요. 넣을지

**확인 뒤 `docs/schema.md`에 넣을 것 (제안)**

- [ ] Item에 `sent: "auto"` (가닥이 직접 보낸 한마디). `/view` 응답에 `auto: {unasked, handoff}` (지금 켜져 있는 종류)
- [ ] 로컬 API: `GET · POST /auto` · `POST /auto/stop` · `POST /auto/start` · `POST /sources/claude-code/connect` · `/disconnect`
- [ ] 로컬 테이블: `auto_log(id, chat_id, item_id, kind, text, created_at)`

**확인한 것**

- 테스트 156개 (보낼지 정하는 로직 · hook이 돌려주는 모양 · 설정 파일에 붙이고 떼기)
- **실제 Claude Code**(가짜 가닥을 세워 두고): 새 대화에 넣은 요약을 모델이 알고 답함 → 턴이 끝날 때 돌려준 글을 이어서 실행함 → 그 뒤에는 다시 보내지 않음
- **실제 엔진**(만든 세션 파일 + 시험용 가닥): “임계값만 바꿔 줘”에 알림 문구까지 바뀐 턴에서, hook이 24.6초 뒤 “notify.py에서 … 원래대로 되돌리고 …”를 돌려줌. 판단 기록에 `get_request` → `get_diff`가 남음
- 화면: 실제 크롬에서 켜는 칸 · ‘가닥이 보냄’ · 끄기 · 찾은 곳의 연결과 끊기를 눌러 봄(설정 파일은 시험용)

**아직 확인하지 못한 것**

- **실제 Cursor.** `followup_message` · `additional_context`는 문서대로 만들었고, Cursor가 hook을 얼마나 기다려 주는지도 몰라요
- 사람이 쓰는 실제 Claude Code 대화(VS Code 확장 화면)에서 처음부터 끝까지. 위 확인은 명령줄(`claude -p`)로 했어요
- 쓰고 있는 실제 `~/.claude/settings.json`에 연결하는 것(시험용 파일로만)
- 웹(크롬 확장) · 데스크톱 앱에서는 가닥이 아직 직접 보낼 수 없어요

## 15. 10/4 (7) — 대화를 목록에서 빼기

시험 삼아 연 대화나 상관없는 폴더의 대화까지 다 보여서 목록이 어지러웠어요. 필요 없는 대화를 목록에서 빼는 기능을 넣었어요. 프로토타입에는 없고 가닥 창에만 있어요.

- 대화 줄에 마우스를 올리면 ×가 보이고, 누르면 그 대화가 빠져요. ‘다른 프로젝트’ 줄의 ×는 그 프로젝트의 대화를 모두 빼요
- 빼면 목록 · 대화 찾기 · 노선도 · 판단 기록에서 사라져요. 정리 호출과 자동 실행도 그 대화에는 쓰지 않고, 이어 가기 요약에 그 대화의 결정이 들어가지 않아요
- **읽어 둔 글은 지우지 않아요.** 지우면 기록 파일을 다시 읽을 때 되살아나서, ‘뺐다’는 표시만 남겨요. 그 대화가 이어져도 다시 나타나지 않아요
- 되돌리기: 뺀 직후의 알림, 또는 목록 맨 아래 ‘뺀 대화 n개’

- [ ] **문구**: ×의 설명 “이 대화를 목록에서 빼기” · “이 프로젝트의 대화를 모두 목록에서 빼기” / 알림 “대화를 목록에서 뺐어요.” · “‘(프로젝트)’의 대화 n개를 목록에서 뺐어요.” · “되돌리기” · “대화 n개를 목록으로 되돌렸어요.” / 목록 아래 “뺀 대화 n개 · 보기 · 접기” · “되돌리기” · “모두 되돌리기”
- [ ] **낱말**: ‘빼기’로 썼어요. 글이 PC에 남으니 ‘지우기’ · ‘없애기’라고 하면 사실과 달라서요. ‘숨기기’가 나을지
- [ ] **완전히 지우기**를 따로 둘지. 지금은 가닥이 읽어 둔 글을 대화 하나만 골라 지울 수 없어요(전부 지우려면 `~/.gadak` 폴더를 지워요)
- [ ] 사용 기록: 빼기를 썼는지는 적지 않아요. 넣을지
- [ ] 확인 뒤 `docs/schema.md`에 넣을 것 (제안): `chats.hidden`, `GET · POST /chats/hidden`, `POST /projects/:id/hide`, `/projects` 응답의 `hidden`(뺀 대화 수)

**아직 확인하지 못한 것**: 사람이 직접 마우스로 누르는 것(크롬에서 스크립트로 눌러 확인), 대화 수백 개를 한꺼번에 뺄 때.

## 16. 10/4 (8) — 떠 있는 가닥 버튼 (다른 앱 위에서 노선도 보기)

노선도를 보려면 일하던 창을 두고 가닥 창으로 가야 했어요. 구현 담당이 그린 스케치(네 장면)대로, 가닥 앱이 **다른 앱 위에 떠 있는 버튼**을 띄우게 했어요. 프로토타입에 없는 화면이고 Mac의 가닥 앱에만 있어요. 쓰는 법은 `docs/usage-guide.md` 5-3.

**스케치와 만든 것**

| 스케치 | 만든 것 |
|---|---|
| 1. 평소: 화면 왼쪽 끝에 반만 보이는 동그라미 | 가닥 버튼이 화면 가장자리에 반쯤 걸쳐 있어요. 보이는 반쪽에 심볼(본선 · 지선 · 빨간 ‘지금’)과 할 일 수가 보여요. 다른 앱을 쓰는 동안에도 그 위에 떠 있어요 |
| 2. 가닥 버튼 활성화 시: ‘가닥’ 버튼과 둘레의 작은 버튼 여섯 | 마우스를 올리면(또는 누르면) 버튼이 다 나오면서 커지고 ‘가닥’ 글자가 보이고, 화면 안쪽으로 반원을 그리며 여섯 개가 펼쳐져요. 마우스가 떠나거나 다른 곳을 누르면 다시 걸쳐요 |
| 3. 버튼 클릭 시: 화면 위쪽에 노선도 | 가닥 버튼이나 둘레 버튼을 누르면 화면 위쪽(메뉴 막대 아래)에 **지금 쓰는 대화의 노선도 카드**가 떠요. 가닥 창의 카드와 같은 화면이에요(`shared/ui`) |
| 4. 버튼은 어디든 이동 가능 (위 · Dock 쪽) | 끌어서 놓으면 가장 가까운 가장자리(왼쪽 · 오른쪽 · 위 · 아래)에 붙어요. 메뉴 막대와 Dock 위에도 놓이고, 자리를 기억해요 |

**스케치와 다르게 한 것**

- **색**: 스케치의 노란색은 펜 색으로 보고, 가닥의 표기대로 그렸어요(종이색 동그라미 · 검은 선 · 심볼 A, 빨강은 ‘지금’과 할 일 수에만). 어두운 화면에서는 어두운 동그라미예요
- **노선도는 카드 위에**: 스케치는 화면에 선만 그렸지만, 다른 앱의 글 위에서는 읽을 수 없어서 노선도 카드(7-9)를 그대로 띄웠어요
- **가장자리에만 붙어요**: ‘어디든’ 중에서 화면 한가운데에는 두지 않아요. 일하는 화면을 가리지 않게 하려고요
- **여섯 버튼**: 스케치에는 번호만 있어서 임시로 채웠어요 — 노선도 · 할 일 · 정함 · 산출물(위쪽 노선도 창에서 그 목록을 같이 보여 줌) · 찾기 · 창(가닥 창을 엶). 가운데 가닥 버튼은 노선도 창을 켜고 꺼요

**무엇이 달라졌나**

| 무엇 | 기존 | 변경 (10/4 밤) |
|---|---|---|
| 노선도 보는 곳 | 가닥 창 | 가닥 창 + 어느 앱 위에서든 위쪽 노선도 창 |
| 창을 닫으면 | 가닥이 꺼짐 (9번) | 버튼이 떠 있는 동안에는 계속 돌아요. 끄려면 ⌘Q나 버튼 오른쪽 클릭 → 가닥 끄기. 버튼을 숨기면 전과 같아요 |
| 메뉴 | 보기: 다시 읽기 · 뒤로 · 앞으로 · 크기 | 보기에 ‘떠 있는 버튼’(켜고 끄기)이 생겼어요 |
| 지금 쓰는 대화 | 가닥 창에서 고른 대화 | 버튼과 위쪽 노선도 창은 **가장 최근에 턴이 온 대화**를 따라가요(목록에서 뺀 것은 건너뜀) |

**파일**: `mac/Float.swift`(버튼 · 위쪽 노선도 창) · `mac/FloatCheck.swift`(앱이 스스로 확인하는 길) · `mac/Gadak.swift`(보기 메뉴, 창을 닫아도 계속 돌기) · `backend/web/strip.html · strip.js · strip.css`(노선도 카드만 띄운 페이지) · `backend/app.py`(`/float` · `/strip`) · `backend/store.py`(`now_chat`) · `backend/web/app.js`(버튼이 가닥 창에 부탁하는 길: 그 역 열기 · 찾기 칸으로) · `backend/macapp.py`(Swift 파일 셋을 같이 컴파일)

## 17. 10/6 — 정확도 평가 (`eval/`)

발표에 쓸 숫자와, 1단을 어느 모델로 돌릴지를 정하려고 만들었어요. 결과와 읽는 법은 README 3-5에 있어요.

**만든 것**

- `python -m eval` — 정답이 달린 실제 대화(u1)를 임시 저장소에 넣고(`backend/replay.py`의 `feed`), 가닥이 평소에 도는 그대로 1단 · 2단을 돌린 뒤, 화면이 받는 값(`/view`와 같은 모양)을 정답과 견줘요. 쓰던 가닥(`~/.gadak`)은 건드리지 않아요
- 지표 넷과 곁 숫자 (`eval/score.py`): depth 정확도(+ 전부 본류라고 답한 값, 곁길 재현율 · 정밀도) · dec 재현율(+ 정밀도) · parts 개수 일치율(+ 요청이 여럿인 턴만) · items 정밀도
- `python -m eval --model sonnet --model haiku`(모델 비교) · `--no-check`(1단만) · `--save`(숫자를 `eval/results/`에) · `--demo`(정답 파일 없이 만든 예시로)
- `python -m eval.agree` — 둘이 따로 단 정답의 일치율. `sheet`로 빈 시트(CSV)를 만들고, 각자 채운 두 시트를 `compare`로 견줘요(일치율과 Cohen의 κ)
- 프롬프트 예시로 쓴 턴 빼기: `docs/agent-prompt.examples.md`의 예시 셋은 u1의 g2 · g3 · g7이에요. `eval/exclude.json`에 적어 두고 평가에서 빼요

**정해 주세요 · 해 주세요 (기획 담당)**

- [ ] **곁길 · 정함의 기준.** 두 모델이 같은 턴에서 틀려요(README 3-5). 프롬프트(`backend/prompts/classify.txt`)의 기준을 다듬을지, 정답을 다시 볼지 정해 주세요. 다듬은 뒤에는 `python -m eval --save --tag 이름`으로 다시 재요
- [ ] **정답 일치율.** `python -m eval.agree sheet`가 만드는 시트(16턴에 ○ 표시)를 둘이 각자 채워요. 시트에는 실제 대화 글이 있어서 `eval/local/`(깃 제외) 밖에 두면 안 돼요
- [ ] **지표의 정의.** 정하지 않은 곳을 이렇게 채웠어요. 다르게 세고 싶으면 알려 주세요
  - depth는 0 · 1 · 2가 정확히 같아야 맞은 것으로
  - dec는 글이 달라도 같은 턴에 정함이 있으면 맞은 것으로
  - items는 같은 턴 · 같은 종류면 맞은 것으로. 빠진 요청(`parts.open`)도 한마디로 세고, 새 대화의 제안(`startTodo`)은 그 대화 첫 턴의 한마디로
  - 가닥이 분류하지 못한 턴은 빼지 않고 화면에 보이는 대로(본류 · 정함 없음 · 나누지 않음) 세요
- [ ] **발표에 쓸 문장.** README 3-5 끝에 제안이 있어요. depth 정확도만 내세우면 안 돼요(전부 본류라고 답한 값과 같아요)

**알아 둘 것**

- 정답 파일의 글은 원문을 줄인 것이에요(질문 평균 54자 · 답 평균 74자). 실제 대화는 더 길어요
- u1의 정답에 있는 한마디 넷 중 지금 가닥이 만드는 종류는 하나(이어 가기)뿐이에요. 그래서 items 정밀도는 숫자가 너무 작아요

## 18. 10/6 — API 키 엔진

## 20. 10/6 — 지난 결정 다시 꺼내기 (‘생각 못 한 방법 추천’의 첫 판 · 꺼 둠)

> **10/7: 이 기능은 접었어요.** 아래에 적은 대로 켜고 재 보니 쓸모가 없어서, 코드(`suggest` 실마리 · `backend/prompts/suggest.txt` · `GADAK_SUGGEST` · `python -m eval --suggest`)를 지우고 **22번의 앞길 살피기**로 다시 만들었어요. 지난 결정을 찾아보는 일은 앞길 살피기의 ‘먼저 보기’에 들어갔어요. 이 절은 왜 접었는지의 기록으로 남겨 둬요.

“학습 데이터 없이 그 사용자의 대화를 근거로 ‘이런 방법도 있어요’”를 가장 좁게 만들었어요: **사용자가 방법을 묻는데, 전에 스스로 정해 둔 것이 있으면 그것을 다시 꺼내 줘요.** 가닥이 아는 일반 지식으로 방법을 권하지는 않아요.

- 2단에 붙였어요(`backend/agent/investigate.py`). 켜는 실마리(`suggest`): 사용자 메시지에 방법을 묻는 말(어떻게 · 방법 · 뭐가 좋 · 추천 · 고민 · 막혔 …)이 있고, 같은 프로젝트의 다른 대화나 이 대화의 꽤 앞(6턴 이상)에 정한 것이 있을 때
- 2단이 `search_decisions`로 지난 결정을 찾아보고, 지금 물음에 맞으면 `next`(다음 할 일) 한마디를 만들어요. 한마디의 글은 엔진의 말이 아니라 기록으로 만들어요: “전에 정한 것이 있어요: “(정한 것)””, 버튼 ‘이 방법으로’, 보낼 글 “전에 정한 대로 해 줘. - (정한 것) (언제 · 어느 대화)”. `at`에 근거가 된 턴이 들어가요
- 이번 걸음에 실제로 찾아본 결정이 아니면 버리고, 버린 까닭을 판단 기록에 남겨요

## 21. 10/6 — 설치하면 바로 켜지는 앱 (디스크 이미지)

지금 앱은 저장소 폴더와 파이썬, Xcode 명령어 도구가 있어야 해서 개발자가 아니면 쓰기 어려웠어요. 받아서 끌어 넣으면 켜지는 앱을 만들 수 있게 했어요. 쓰는 법은 `docs/usage-guide.md` 1-1.

| 무엇 | 저장소에서 쓰는 앱 (‘가닥 설치.command’) | 건네는 앱 (`python -m backend.macapp --dmg`) |

| 백엔드 | 저장소 폴더의 코드를 파이썬으로 | 앱 안의 실행 파일 (`Contents/Resources/backend/gadak-backend` · PyInstaller) |

- 내 `.env`(서버 주소 포함)와 실제 대화는 앱에 들어가지 않아요. 사용 기록을 받을 서버 주소를 넣으려면 만들 때 `--collect`를 붙여요(기본은 넣지 않음 → 받은 사람의 가닥은 사용 기록을 묻지도 보내지도 않아요)

## 22. 10/7 — 앞길 살피기 (‘생각 못 한 방법 추천’을 다시 만듦 · 누를 때 한 번, 켜 두면 저절로)

20번을 접고 다시 만들었어요. 방향은 구현 담당이 정했어요: **“작업을 하면서 사용자가 무엇을 하려고 하는지 읽고, 그 방향에서 어떻게 나아갈 수 있는지 예측해서, 여러 방향성을 미리 찾아보고 조사해 내민다.”**

20번과 다른 점은 둘이에요. ① 지난 결정을 되풀이해 주는 게 아니라, **사용자와 LLM이 지금 보고 있지 않은 것**(미뤄 둔 일 · 정해 둔 것과 어긋남 · 바깥의 다른 방법)을 찾아다 줘요. ② 낱말이 아니라 **갈림길**에서 돌아요.

### 22-1. 구조 — 다섯 걸음

| 걸음 | 무엇 | 누가 | 호출 |
|---|---|---|---|
| 1. 갈림길 잡기 | 방금 정함 · 구간이 바뀜 · 사용자가 “다음에 뭐 하지”를 물음. 또는 사용자가 ‘앞길 보기’를 누름 | 코드 (`ahead.due`) | 없음 |
| 2. 먼저 보기 | 이 프로젝트에서 정해 둔 것, 열린 할 일, 작업 폴더 문서의 목차(계획 · 일정 · 미정 · 규칙이 적힌 제목과 줄 번호) | 코드 (`ahead.opening`) | 없음 |
| 3. 목적지 읽기 · 더 찾아보기 | ‘이 대화가 향하는 곳’을 한 줄로 읽고, 더 읽을 대목 · 찾아볼 것을 골라요(문서의 한 대목 읽기 · 지난 물음 찾기 · 웹에서 찾아보기) | 엔진 (도구 루프 · 최대 8걸음) | 보통 2~3번 |
| 4. 길 내기 | 성격이 다른 길을 셋까지: **이어 가기**(계획 · 남은 일에 있는데 아직 안 한 것) · **다른 길**(같은 목적지로 가는 다른 방법) · **미리 챙길 것**(기한 · 정해 둔 것과 어긋남 · 확인 안 된 가정) | 엔진 | |
| 5. 근거 검사 · 내밀기 | 아래 22-2의 규칙으로 거르고, 남은 길을 ‘다음 할 일’(next) 한마디로 | 코드 (`ahead.conclude`) | 없음 |

- 코드는 `backend/agent/ahead.py`(본체) · `backend/agent/outside.py`(기록 밖을 보는 도구) · `backend/prompts/ahead.txt`(프롬프트 · **구현 담당의 초안**)에 있어요.
- 2단 일꾼(`investigate.py`)이 돌려요. 1단이 갈림길이라고 본 턴은 `look`에 `ahead`가 붙고, 사용자가 누른 것은 `POST /chats/:id/ahead`로 줄을 서요.
- **가닥은 여전히 대답하지 않아요.** 길은 답이 아니라 쓰고 있는 LLM에게 가져갈 물음(‘보낼 글’)이에요. 보내기는 사용자가 정하고, 가닥이 대신 보내는 종류(`store.AUTO_KINDS`)에 넣지 않았어요.

### 22-2. 무엇을 버리나 (근거 검사)

- 근거가 된 턴이 이번에 엔진에게 보여 준 기록에 없으면 그 길을 버려요.
- ‘찾아본 것’의 출처는 도구가 실제로 돌려준 것이어야 해요: 지난 턴 · 파일(경로) · 웹 주소. 웹 주소는 검색 도구가 돌려준 결과에 실제로 있던 것만 남겨요(엔진이 적은 주소를 검색 결과와 대조해요).
- **‘찾아본 것’은 지금 대화 밖에서 와야 해요.** 이 대화의 최근 10턴은 사용자가 이미 아는 것이라 출처로 치지 않아요. 다른 대화, 10턴 넘게 앞의 턴, 파일, 웹만 쳐요.
- 찾아본 줄의 글은 엔진이 간추린 말이에요. 파일 · 웹에서 찾았다는 줄에 든 수(두 자리 넘는 수 · `#번호` · 퍼센트)가 그 출처의 글에 없으면 그 줄을 빼요.
- **찾아본 것이 한 줄도 없는 길은 버려요.** 하나도 안 남으면 아무 말도 하지 않아요.
- 같은 종류의 길은 하나만. 버린 까닭은 판단 기록(`/trace`)에 남아요.

이 규칙들은 시범에서 실패하면서 생겼어요(22-5).

### 22-3. 조사하는 범위와 안전장치

| 범위 | 언제 | 안전장치 |
|---|---|---|
| 내 기록 | 늘 | 같은 프로젝트 안에서만. 목록에서 뺀 대화는 안 봐요. 그 턴 뒤의 기록은 안 봐요 |
| 작업 폴더의 파일 | 그 대화에 작업 폴더가 있을 때 (`GADAK_AHEAD_FILES=0`으로 끔) | 읽기만. 폴더 밖 · 깃이 무시하는 파일 · 비밀처럼 보이는 이름(`.env` · `*.pem` · `*.local.*` · secret · token …) · 글이 아닌 파일 · 300KB 넘는 파일은 안 읽어요. 홈 · 바탕화면 · 문서 · 다운로드 같은 넓은 폴더에서 연 대화에서는 아예 안 읽어요. 깃을 쓸 수 없는 Mac(개발자 도구 없음)에서는 깃을 부르지 않고(설치 창이 뜨지 않게), 저장소 안의 파일은 읽지 않아요. 읽은 글은 대화 글과 같은 곳(엔진)에만 가요 |
| 웹 | `GADAK_AHEAD_WEB=1`로 따로 켰을 때만 | 검색만 해요(페이지를 열거나 명령을 돌리지 않아요). 한 번 살필 때 두 번까지. 프롬프트가 사람 이름 · 회사 이름 · 대화의 문장을 검색어에 넣지 말라고 해요. **그래도 대화에서 뽑은 검색어가 밖으로 나가요** — 그래서 기본은 꺼 뒀어요. Claude 구독 엔진에서만 돼요 |

### 22-4. 화면에 나오는 것 — 전부 임시 문구예요

- [ ] 한마디의 글: `이어 가기 · (길 이름)` / `다른 길 · (길 이름)` / `미리 챙길 것 · (길 이름)`. 라벨은 기존대로 ‘다음 할 일’
- [ ] 한마디의 버튼: `이 길 보기` → 창이 떠요
- [ ] 창: 제목 `앞길 · (종류)`, 본문은 `지금 하려는 일`(가닥이 읽은 목적지) · 길과 까닭 · `근거`(어느 턴) · `찾아본 것`(줄마다 출처) · `보낼 글`. 안내 글: `가닥이 미리 찾아본 길이에요. 답이 아니라 물어볼 거리라서, 고쳐서 보내도 돼요.` 실행 버튼: `이 길로 묻기`
- [ ] 보낼 글 끝에 붙는 말: `참고로 미리 찾아본 것이야. 맞는지도 같이 봐 줘.` 그 아래 찾아본 줄과 출처(웹은 주소 그대로)
- [ ] 할 일 목록 아래의 줄(임시 자리): 제목 `앞길`, 글 `지금 자리에서 갈 수 있는 길`, 버튼 `앞길 보기`. 누르면 `앞길을 살펴보고 있어요. 1~2분 뒤 ‘제안’에 나타나요. 찾은 것이 없으면 아무것도 안 떠요.` 켜져 있을 때만 보여요
- [ ] 판단 기록의 도구 이름: `지난 물음 찾기` · `파일 목록 보기` · `파일에서 찾기` · `파일 읽기` · `웹에서 찾아보기`. 가닥이 먼저 본 걸음에는 `가닥이 늘 먼저 보는 것이에요.`
- [ ] 판단 기록 페이지에 더한 말: 확인한 까닭 `앞길 살피기` + `방금 정했어요` · `구간이 바뀌었어요` · `다음 할 일을 물었어요` · `앞길 보기를 눌렀어요`, 그 아래 `읽은 목적지 · (목적지)`
- [ ] 버린 까닭: `근거가 된 턴이 이번에 본 기록에 없어서 버렸어요` · `찾아본 것이 없는 길이라 버렸어요` · `같은 종류의 길이 이미 있어서 버렸어요` · `출처로 칠 수 없는 줄 n개를 뺐어요 (길은 남겼어요)` …
- 프로토타입과 다른 점: 프로토타입의 ‘다음 할 일’은 버튼을 누르면 바로 글이 들어가요. 여기서는 창을 한 번 거쳐요(근거와 찾아본 것을 보고 보내게). 노선도에 앞길을 점선으로 그리는 것은 하지 않았어요(디자인 담당과 정할 것).

### 22-6. 켤지 정하는 법 — 두 분이 매겨 주세요

**기준**: **둘이 따로 매겨서, 둘 다 쓸모 있다고 한 길이 70% 이상(둘 다 매긴 길이 10개 이상일 때)이면 켜요.** 구현 담당이 고른 기준이에요.
예시 대화(u1)는 기획 담당이 한 대화라, 구현 담당은 그 순간의 맥락을 모르고 매겨요. 그래서 둘이 얼마나 같게 매겼는지(κ)를 같이 보고, 크게 갈리면 갈린 줄을 같이 봐요.
(10/7 낮에 ‘그 대화를 한 사람 혼자 매기기’로 잠깐 바꿨다가, 구현 담당도 매기기로 하고 다시 둘로 돌렸어요.)

**한 사람의 첫 채점 (10/7 · 기획 담당 · 먼저 낸 7개)** — `python -m eval.ahead score eval/local/앞길-A.csv`

| | |
|---|---|
| 쓸모 있다고 한 길 | **5 / 7 (71%)** — 한 사람의 숫자예요. 두 사람의 시트를 견준 것은 아래 ‘판정’에 있어요 |
| 종류별 | 이어 가기 2/2 · 미리 챙길 것 2/3 · 다른 길 1/2 |
| 쓸모 있는데 실제로는 가지 않은 길 (‘생각 못 한 길’) | 3개 — s16의 둘(데이터 구조로 옮기기 · 기존 도구의 UX 참고) · s37(확장 아이콘의 애니메이션) |
| 쓸모없는데 실제로 간 길 (뻔한 되풀이) | 1개 — s29(확장 프로그램 형식 확인): “이미 앎” |
| 쓸모없다고 한 다른 하나 | s8(선행 사례와 차별점): “막연함: 후보가 조건에 딱 맞지 않아 하나씩 다시 따져야 했음” |
| 갔나를 비운 것 | s47의 둘 — 그 뒤 대화가 세 턴뿐이라 알 수 없음 |

채점하다 나온 것 둘:

- **출처가 어긋난 줄이 하나 있었어요.** s37의 “크롬 확장 아이콘은 GIF 애니메이션이 재생되지 않는다”는 내용은 맞는데, 출처로 든 크롬 공식 문서에는 그 말이 없어요(지원 형식에 GIF가 있다는 말만 있어요). 웹에서 찾아보기는 검색 결과의 요약만 보고 줄을 적고, 가닥은 그 주소가 검색 결과에 있었는지만 대조해요. 고칠 길은 둘이에요: ① 그 페이지를 열어 그 말이 있는지 대조하기(호출과 시간이 더 들어요) ② 웹에서 찾은 줄에는 출처를 ‘근거’가 아니라 ‘검색에서 본 곳’이라고 적기. 평가가 끝날 때까지는 조건을 바꾸지 않으려고 손대지 않았어요
- 다른 하나의 주소(s16 · Medium)는 403으로 열리지 않았어요

**10개를 채우려고 더 낸 것 (10/7 오후)**: 한 대화에서 갈림길을 8턴에 한 번까지 보는 규칙이라 u1에서는 여섯 곳뿐이에요. 간격을 4턴으로 줄여(`GADAK_AHEAD_EVERY=4`) 그 사이의 다섯 곳(s12 · s20 · s44 · s49 · g5)을 더 살폈고, 길 8개가 나왔어요(이어 가기 2 · 다른 길 2 · 미리 챙길 것 4). 기획 담당이 매긴 시트의 사본 뒤에 붙였어요 → `eval/local/앞길-A-이어서.csv` (15줄: 매긴 7 + 새 8). 구현 담당이 채울 것은 같은 15줄에서 매긴 칸을 비운 `eval/local/앞길-B.csv`예요. Sonnet 13번 + 웹 5번, API로 치면 $0.77이에요. 사이의 갈림길이라 앞뒤 갈림길의 길과 내용이 겹칠 수 있어요.

**판정 (10/7 오후 · 둘 다 매긴 7개로)** — `python -m eval.ahead compare eval/local/앞길-A-이어서.csv eval/local/앞길-B.csv --need 7`

| | |
|---|---|
| 둘 다 매긴 길 | 7개 — 먼저 낸 것 전부. 더 낸 8개는 한 사람만 매겨서 빠졌어요 |
| 둘 다 쓸모 있다고 한 길 | **5 / 7 (71%)** → 70% 기준을 넘음 |
| 한 사람씩 · 일치 | 기획 담당 5/7 · 구현 담당 5/7 · 7개 모두 같게 매김(κ 1.00) |
| 종류별(둘 다 쓸모) | 이어 가기 2/2 · 미리 챙길 것 2/3 · 다른 길 1/2 |
| 실제로는 가지 않았지만 둘 다 쓸모 있다고 한 길 | 3개 |

**정해 둔 조건을 다 채운 판정이 아니에요.** 둘 다 매긴 길이 10개가 안 돼서 `compare`는 그대로 돌리면 “아직 정할 수 없어요”라고 해요. 구현 담당이 지금 있는 채점만으로 판정하기로 해서, 최소 개수를 이번만 7로 낮췄어요(`--need 7`). 도구도 결과에 “정해 둔 최소(10개)보다 적은 7개로 낸 판정”이라고 같이 적어요. 읽을 때의 한계 셋:

- **7개예요.** 둘 다 쓸모 있다고 한 길이 하나만 적었어도 4/7(57%)로 못 미쳐요
- **따로 매긴 일치가 아니에요.** 구현 담당은 기획 담당이 보낸 결과 요약(쓸모 5/7 · 어느 줄에 0을 줬고 왜인지)을 본 뒤에 이 7줄을 매겼어요. 7줄이 모두 같게 나온 것(κ 1.00)을 두 사람이 따로 같은 판단에 이른 것으로 읽으면 안 돼요
- **예시 대화 하나예요.** u1(기획 담당의 대화)의 갈림길 여섯 곳에서 나온 길이에요

**더 낸 8개는 판정에 넣지 않았어요.** 구현 담당만 매겼어요: 처음에는 8개 중 6개가 쓸모(15개 전체로는 11개 · 73%)였고, 같은 날 다시 매기면서 0이던 둘(s49의 이어 가기 · g5의 다른 길)을 1로 고쳐 8개 모두 쓸모(13/15 · 87%)가 됐어요. 한 사람의 숫자라 판정의 근거로 쓰지 않았어요. 기획 담당이 `앞길-A-이어서.csv`의 아래 8줄을 매기면 `--need` 없이 15개로 다시 견줄 수 있어요.

**그래서 누를 때만 돌게 했어요 (10/7 오후 · 구현 담당).** 한 곳을 살피는 데 구독 한도를 얼마나 쓰는지 재 봤어요. 예시 u1의 갈림길 3곳을 웹 없이 살피고, 그 앞뒤로 Claude Code가 응답마다 알려 주는 사용률(`rate_limit_event`의 `unifiedWindows.five_hour.utilization`)을 읽었어요.

| | 3곳 합계 | 한 곳 |
|---|---|---|
| Claude Pro 5시간 한도의 사용률 | 83% → 85% | 0.7%쯤 (사용률이 1% 단위라 0.3~1%) |
| Sonnet 호출 · 시간 | 8번 · 81초 | 2~3번 · 27초쯤 |
| API로 치면 | $0.25 | 8센트쯤 |

58턴 대화 하나에 갈림길이 여섯 곳이니, 저절로 살피면 대화 하나에 4%쯤이 사용자가 모르는 새 나가요(같은 대화의 1단 정리는 API 값의 비율로 치면 2%쯤). 그래서 갈림길에서 저절로 도는 것은 끄고(`GADAK_AHEAD_AUTO=1`로 다시 켤 수 있어요), 사용자가 ‘앞길 보기’를 눌렀을 때만 돌게 했어요. 버튼은 기본으로 보여요(`GADAK_AHEAD=0`으로 감춰요). 누르면 작업 폴더의 문서를 읽어요(22-3). 웹은 여전히 따로 켜요. 웹을 켠 경우(한 곳에 11~15센트)는 한도로 재지 않았어요.

**두 방식을 다 뒀어요 (10/7 오후 · 구현 담당).** 가닥 창 맨 위 검은 머리띠의 ‘전체 지도’ 옆에 버튼이 둘 있어요. (같은 날 저녁에 자리를 옮겼어요: ‘앞길 보기’는 목록의 ‘앞길’ 칸 맨 위, ‘저절로 살피기’는 ‘할 일’ 칸 아래 → 23번. 아래는 처음 둔 자리의 기록이에요.)

- **저절로 살피기 끔 · 켬** — 누르면 바뀌어요. 켜 두면 길이 갈리는 순간(방금 정함 · 구간이 바뀜 · 다음 할 일을 물음)마다 살펴요. 한도를 더 쓰는 쪽이라 기본은 끔이고, 켜져 있으면 흰 바탕으로 보여요. 가닥이 기억해요(settings의 `ahead.auto`. 고른 적이 없으면 `GADAK_AHEAD_AUTO`)
- **앞길 보기** — 저절로 살피기를 꺼 둔 동안에만 그 옆에 보여요. 누른 그 시점의 자리(그 대화의 마지막 턴)에서 한 번 살펴요
- 찾은 길은 전과 같이 할 일 목록의 ‘제안’에 ‘다음 할 일’로 떠요. 할 일 목록 아래에 있던 임시 줄은 가닥 창에서 뺐어요(`shared/ui`의 hooks `ahead` · `aheadOn`은 남아 있어요)
- 프론트 담당이 쓸 것: `GET /status`의 `ahead.auto`, `POST /ahead/auto {"on": true|false}`, `POST /chats/:id/ahead`. 가닥 창에서는 `backend/web/app.js`의 `paintAhead` · `toggleAheadAuto`가 그려요
- [ ] 자리와 문구(‘저절로 살피기 끔 · 켬’ · ‘앞길 보기’ · 풍선 글 · 토스트)는 임시예요. 따로 띄운 가닥에서 두 상태를 화면으로 확인했고, 사람이 눌러 보는 것은 아직이에요

**하는 법**

1. 시트 만들기: `python -m eval.ahead run --web` → `eval/local/앞길-시트.csv` (길마다 한 줄. 실제 대화 글이 들어 있어서 깃에 안 올라가요)
   - 내가 쓰는 가닥의 기록으로 만들려면: `python -m eval.ahead run --records ~/.gadak/gadak.db --max 6 --web` (기록은 읽기만 하고 복사본으로 돌려요. 목록에서 뺀 대화는 안 봐요. `--web`을 붙이면 내 대화에서 뽑은 검색어가 밖으로 나가요)
   - 1단을 다시 부르지 않으려면 `--db eval/local/u1.db` (정리한 기록을 남겨 두고 다시 써요)
   - 길이 모자라면: `GADAK_AHEAD_EVERY=4 python -m eval.ahead run --max 20 --web --db eval/local/u1.db --append --out <매긴 시트>` — 시트에 이미 있는 갈림길은 다시 살피지 않고, 있던 줄과 매긴 값은 그대로 둔 채 새 줄만 뒤에 붙여요. 다른 사람이 채울 시트는 그 파일에서 `쓸모` · `갔나` · `메모` 칸을 비운 사본이에요(같은 줄이어야 견줄 수 있어요. 다시 돌리면 길이 달라져요)
   - 멈춘 데서 이으려면 `--from 6 --append`, 다른 대화를 더하려면 `--scenario u4 --append`
2. 매기기: 두 사람이 같은 시트를 각자 복사해서, 서로 보지 않고 두 칸을 채워요
   - `쓸모`: 1 쓸 만해요 · 0 아니에요 (뻔해요 · 틀렸어요 · 이미 아는 거예요). 그 턴에 서 있다고 생각하고, ‘그 뒤 실제 대화’는 보기 전에 매겨요
   - `갔나`: ‘그 뒤 실제 대화’ 칸을 보고, 실제로 그 길로 갔으면 1 · 아니면 0 · 모르겠으면 비워요
   - 두 칸은 `1`이나 `0`으로 시작하게 적어요(`O` · `X` · `예`는 못 읽어요). `번호` · `턴` · `종류` 칸은 고치지 않아요. `메모`는 자유예요(프로그램이 읽지 않아요. 0을 준 까닭을 한마디 적어 주면 프롬프트를 고칠 때 써요)
   - 다 채웠으면 `python -m eval.ahead check <시트>` — 시트가 읽히는지, 읽지 못한 칸이 있는지 알려 줘요. 엑셀 · Numbers로 저장한 것도 읽어요(CSV UTF-8 · 예전 한글 형식 · 유니코드 텍스트). `.xlsx`는 못 읽어요
   - 시트는 깃이 아니라 직접 주고받아요(실제 대화 글이 들어 있어요. `eval/local/`은 깃이 무시하고, 어느 가지의 기록에도 올라간 적이 없어요)
3. 견주기: `python -m eval.ahead compare A.csv B.csv` → 둘 다 쓸모 있다고 한 비율과 켤 기준을 넘는지, 한 사람씩의 비율, 일치도(κ), 실제로 간 길의 비율, ‘가지 않았지만 쓸모 있다고 한 길’(생각 못 한 길)의 수. 읽지 못한 칸이나 한쪽 시트에만 있는 길이 있으면 같이 알려 줘요. 한 사람만 돌리면 돼요
   - 한 사람의 시트만 보려면 `python -m eval.ahead score <시트>` (쓸모 있다고 한 비율 · 종류별 · 생각 못 한 길 · 뻔한 되풀이의 수. 켤지는 말하지 않아요)
   - 둘 다 매긴 길이 10개가 안 되는데 있는 것으로 판정해야 하면 `--need 7`처럼 최소 개수를 낮춰요. 낮춰서 낸 판정이라는 것과, 하나만 달랐어도 판정이 달라지는지를 결과에 같이 적어요

- [ ] 처음에 같이 적었던 “호출이 10% 넘게 늘지 않으면”은 이 구조에서는 맞출 수 없어요(갈림길마다 큰 모델을 2~4번 불러요). 대신 **갈림길 한 곳의 값**(지금 6~15센트)과 **하루에 몇 번 도는지**를 보고 정하는 쪽을 제안해요. 정해 주세요
- [ ] 예시 대화 하나(기획 담당의 대화)로 켤지 정하게 돼요. 구현 담당의 기록으로도 길을 만들어 매길지(`--records`) 정해 주세요
- [ ] 출처가 어긋난 줄(위)을 어떻게 할지: 페이지를 열어 대조 / ‘검색에서 본 곳’이라고 적기 / 그대로 두고 “맞는지도 같이 봐 줘”에 맡기기
- [ ] 한 번 돌리는 데 Claude 구독 한도를 꽤 써요. 10/7 하루에 시범 · 평가로 엔진을 110번쯤 불렀고(Sonnet 50 · Haiku 60쯤) 한도에 한 번 걸렸어요

### 22-7. 프론트 담당이 쓸 것

| 무엇 | 모양 |
|---|---|
| 켜져 있나 | `GET /status` → `ahead: {on, web, files}` · `classify.aheadQueued`(눌러서 기다리는 대화 수) |
| 앞길 보기 | `POST /chats/:id/ahead` (본문 `{}`) → `{ok: true}`. 꺼져 있거나 엔진이 없으면 409와 `{ok: false, reason}`. 결과는 1~2분 뒤 그 대화 마지막 턴의 할 일로 와요(`rev`가 바뀌어요) |
| 길 | 기존 Item 그대로: `kind: "next"`, `text`, `why`, `btn`, `pop: {title, text, note, btn, prompt}`. id만 `<turnId>:a<n>` |
| 판단 기록 | `/runs`의 한 줄에 `trigger: ["ahead"]`와 `goal`(읽은 목적지) · `why`(살핀 까닭) · `paths`(낸 길과 근거 · 출처)가 더 실려요. 가닥이 먼저 본 걸음은 `steps`의 앞쪽에 있어요 |

| `GADAK_AHEAD_EVERY` | `8` | 저절로 살피기를 켰을 때, 한 대화에서 이만큼의 턴에 한 번까지 (누른 것은 세지 않아요) |
| `GADAK_AHEAD_STEPS` | `8` | 한 번 살필 때 엔진에 묻는 걸음 수의 한도 |
| `GADAK_AHEAD_FRESH` | `180` | 분. 이보다 오래된 턴은 살피지 않아요(지난 대화를 한꺼번에 정리할 때 대화마다 돌지 않게) |

### 22-10. 같이 고친 것

- 엔진이 형식을 여러 번 다시 시켜도 못 맞춘 경우(Claude Code의 `error_max_structured_output_retries`)를 그 묶음만의 실패로 세요. 전에는 정리 전체가 멈췄어요. 시범에서 Haiku가 `"arg": ,`처럼 깨진 JSON을 낸 것이 계기예요(프롬프트의 “비워”를 글자 그대로 따랐어요. “null”이라고 쓰게 고쳤어요)
- 정확도 평가의 `--suggest`를 없앴어요

### 22-11. 아직 확인하지 못한 것

- **사람이 매긴 쓸모.** 둘 다 매긴 길은 7개뿐이고, 그것도 따로 매긴 것이 아니에요(22-6). 더 낸 8개는 한 사람만 매겼어요. 정해 둔 10개를 채운 판정은 아직 없어요
- **웹에서 찾은 줄의 출처가 그 말을 담고 있는지.** 확인하지 않아요. 채점에서 어긋난 것이 하나 나왔어요(22-6)
- **실제로 쓰면서 갈림길에서 저절로 도는 것.** 갈림길 잡기와 일꾼은 테스트로 확인했고, 실제 엔진으로는 직접 불러서만 돌렸어요(켜 둔 채 며칠 써 보지 않았어요)
- **화면에서 사람이 눌러 보는 것.** ‘앞길 보기’ 줄과 길이 뜨는 것은 따로 띄운 가닥을 크롬으로 열어 확인했고, 누르는 것은 테스트로만 확인했어요
- **API 키 엔진.** 길 찾기는 같은 방식으로 돌게 돼 있지만 불러 보지 못했고, 웹에서 찾아보기는 이 엔진에 없어요
- **‘찾아본 것’의 글이 원문과 같은지.** 출처(어느 턴 · 어느 파일 · 어느 주소)는 가닥이 실제로 본 것인지 대조하지만, 그 줄의 글은 엔진이 간추린 말이에요. 일꾼 경로를 실제 엔진으로 돌려 본 한 번에서, README의 한 줄을 옮기며 PR 번호를 틀리게 적었어요(출처는 맞았어요). 그 뒤로 파일 · 웹의 줄은 수를 대조해서 걸러요(22-2). 수가 아닌 말이 달라진 것은 못 걸러요. 웹은 주소가 검색 결과에 있었다는 것과 수까지만 확인하고, 그 페이지를 열어 보지는 않아요. 그래서 보낼 글에 “맞는지도 같이 봐 줘”를 붙여요. 원문의 줄을 그대로 싣는 쪽이 나은지 정해야 해요
- 길의 글(이름 · 까닭 · 찾아본 줄 · 보낼 글)에 가닥 안에서만 쓰는 턴 id(`t9fd…`)가 그대로 나온 일이 있어서(더 낸 길 가운데 한 줄의 까닭), 그 턴의 제목으로 바꿔 보여 주게 고쳤어요. “seq36”처럼 차례 번호로 적는 것은 아직 그대로 나와요(프롬프트에서 제목으로 가리키라고 해야 해요)
- **일꾼 경로는 한 번 돌려 봤어요.** 실제 기록의 복사본에서 ‘앞길 보기’를 누른 것과 같은 길을 실제 엔진으로 돌려, 한마디 둘과 판단 기록이 남는 것을 봤어요(Sonnet 2번 · 31초)
- **대화가 아주 긴 경우 · 작업 폴더가 아주 큰 경우의 값과 시간**

### 23-1. 무엇을 바꿨나

### 23-2. ‘앞길 보기’가 왜 아무것도 안 띄웠나

- 구현 담당의 기록에는 앞길의 판단 기록이 한 건도 없었어요. 한 번도 끝까지 돌지 못한 거예요
- 같은 기록의 사본에서 실제 엔진으로 눌러 보니 정상이었어요(33초 · Sonnet 2번 · 길 2개). 그때 실패한 까닭은 남아 있지 않아요. 눌렀던 무렵에 구독 한도가 거의 찼던 것은 맞아요
- 원인은 **실패가 보이지 않는 구조**였어요: 누른 요청은 줄에서 꺼낸 뒤에 살피는데, 살피다 실패하면 판단 기록도 할 일도 남지 않았어요. 이제 실패도 까닭과 함께 ‘앞길’ 칸에 떠요

### 25-2. 기획 담당의 코드에서 달라진 곳

- **반복 질문 (`backend/agent/rules.py` · 구현 담당이 정함)**: 한 대화에서 이어진 대화(fork)끼리는 ‘지난 대화’로 치지 않아요. 지난 대화를 찾는 조건을 `c.created_at <= ?`에서 `<`로 바꾸고, 이 턴을 그대로 담은 대화(같은 자리 · 같은 글)를 빼는 조건을 더했어요. 그 조건이 대신하게 된 두 줄(`continue`)은 뺐어요.
  - 까닭: Claude Code에서 대화를 이어 받으면 새 대화가 앞 대화의 턴을 처음부터 그대로 담아서 **만든 시각이 같아요.** `<=`라서 서로를 지난 대화로 봤고, 똑같은 턴 하나만 건너뛰어서 같은 대화의 이름이 비슷한 옆 턴과 짝지어졌어요.
  - 재 본 것: 구현 담당의 기록 사본(숨기지 않은 대화 24개 · 정리된 327턴)에 규칙을 한꺼번에 돌리면 반복 질문이 28개에서 9개가 돼요. 빠진 19개는 모두 한 대화에서 이어진 네 대화(44 · 48 · 54 · 90턴)에서 나온 것이에요. 테스트는 `test_chats_carried_on_from_one_another_are_not_earlier_chats`.
- **구간 다시 나누기 (`backend/agent/classify.py`)**: 형식이 틀린 답(`BadOutput`)이 오면 구간을 그대로 두고 정리를 이어 가요. 그 예외가 없던 가지에서 쓴 코드라, 그대로 합치면 그런 답이 올 때 그 대화의 2단 확인이 건너뛰어졌어요.
- **토큰 기록**: 적는 종류가 늘었어요. `classify` · `segment` · `check` · `handoff`에 더해 `ahead`(앞길 살피기) · `lookup`(웹에서 찾아보기) · `gist`(답 간추림 채우기)예요. 형식이 틀려 다시 물은 호출과 실패한 답의 토큰도 더해서 적고, API 키 엔진도 같은 모양으로 남겨요.
- **‘환승하기’ (`shared/ui/nudge.js` · `backend/web/strip.js`)**: 주제 전환 한마디의 ‘환승하기’가 가닥 창에서만 됐어요. 떠 있는 버튼의 목록 창에는 노선도 끝의 환승 표시(`handoff` hook)가 없어서 빈 글이 복사됐어요. 같은 요약을 복사하게 `transfer` hook을 더했어요(그 창의 노선도에는 환승 표시를 그리지 않아요).
- **평가 (`eval/`)**: 구간을 다시 나누는 호출을 1단과 따로 세요(‘구간 나누기 n번’). ‘가닥이 만드는 종류’에 규칙 할 일 셋을 더했어요(`eval/score.py`의 `MADE`).

### 26-2. AI 연결 (`backend/web/app.js` · `backend/engines/`)

**화면** — 가닥 창 왼쪽 아래에 ‘AI 연결’ 버튼이 생겼어요(쓸 수 있는 AI가 없으면 검은 버튼). 누르면 ‘찾은 곳’과 같은 자리에 카드 셋이 떠요. 바로 쓸 수 있는 AI가 하나도 없으면 처음 켤 때 저절로 떠요.

| 카드 | 상태 글 | 버튼 |
|---|---|---|
| Claude 구독 (Pro · Max) | 아직 연결하지 않았어요 · 로그인만 하면 돼요 · 연결됨 · Pro · 지금 쓰는 중 · … | 연결하기 · 그만두기 · 이걸로 정리하기 |
| ChatGPT 구독 (Plus · Pro) | 위와 같아요 | 위와 같아요 |
| API 키 (Anthropic) | 키를 넣으면 바로 써요 · 연결됨 · sk-ant-…끝 네 글자 | 저장 · 이걸로 정리하기 · 키 지우기 |

- 맨 위 한 줄: “가닥이 대화를 정리할 때 쓰는 AI예요. 하나만 연결하면 돼요. 지금은 ○○으로 정리해요 (가닥이 알아서 골랐어요).”
- 맨 아래: 알아서 고르기 · AI 없이 쓰기 · 닫기
- 연결하는 동안의 글: “Claude Code를 받고 있어요. 1~2분 걸려요…” → “브라우저에서 로그인을 마쳐 주세요. 끝나면 여기가 저절로 바뀌어요.” → “○○을 연결했어요. 이제 이 AI로 정리해요.”
- 안 됐을 때: “○○를 받지 못했어요. 인터넷을 확인하고 다시 눌러 주세요.” · “5분 안에 로그인이 끝나지 않았어요. 다시 눌러 주세요.” · “로그인이 끝나지 않았어요. 브라우저에서 로그인을 마친 뒤 다시 눌러 주세요.”
- 상태 줄의 글도 바꿨어요: “정리 엔진이 없어서 제목이 임시예요. docs/usage-guide.md 3번을 봐 주세요.” → “정리할 AI가 연결되지 않아서 제목이 임시예요. ‘AI 연결’을 눌러 주세요.”

**한 번 눌러 연결** (`backend/engines/connect.py`) — 사용자가 ‘연결하기’를 눌렀을 때만 돌아요.

1. 없으면 받아요. Claude Code는 Anthropic의 공식 설치 스크립트(`https://claude.ai/install.sh`)를 받아 돌리고(받은 파일의 검사는 그 스크립트가 해요), Codex는 OpenAI의 공식 배포 파일(`github.com/openai/codex`의 releases)을 `~/.gadak/bin/codex`에 풀어요. https로, 이 두 주소에서만 받아요.
2. 로그인 창을 띄워요(`claude auth login` · `codex login`). 브라우저가 열리고, 로그인은 사용자가 거기서 해요. 가닥은 암호도 토큰도 보지 않아요.
3. 다 되면 그 엔진을 고른 것으로 적어요.

한 번에 하나만 돌고, 5분 안에 로그인이 끝나지 않으면 멈춰요. 어디까지 갔는지는 `GET /engine`의 `job`에 나와요.

**ChatGPT 구독 엔진** (`backend/engines/codex_cli.py`) — 내 PC의 Codex를 `codex exec`로 불러요. 기록을 남기지 않고(`--ephemeral` — 가닥이 그 기록을 대화로 다시 읽지 않게), 내 설정을 싣지 않고, 읽기 전용으로 돌려요. 답의 형식은 `--output-schema`로 정해요. Codex는 터미널 명령이 없어도 VS Code · Cursor의 ChatGPT 확장 안에 들어 있는 것을 찾아 써요. 가닥의 모델 이름(haiku · sonnet · opus)은 생각 깊이로 옮기고, 모델은 Codex의 기본값이에요.

**고르기** — 화면에서 고른 것은 settings의 `engine.choice`에 남고 설정(`GADAK_ENGINE`)보다 먼저예요. 고르지 않았을 때 `auto`의 차례: Claude 구독 → API 키 → ChatGPT 구독 → 없음.

**길** — `GET /engine`(+ `options`: 엔진마다 `found` · `ready`, `job`: 연결이 어디까지 갔는지, `choice`) · `POST /engine/choose {name}` · `POST /engine/connect {name}` · `POST /engine/cancel` · (있던 것) `POST` · `DELETE /engine/key`.

### 26-3. 떠 있는 버튼 편집 (`backend/floatbar.py` · `mac/Float.swift` · `backend/web/float-edit.html`)

- **여섯 자리**를 사용자가 골라요. 자리마다 기능 하나(노선도 · 할 일 · 정함 · 산출물 · **앞길** · 찾기 · 창 · **도움말**)나 프로젝트 하나. 처음 모양은 전과 같은 여섯이에요.
- **프로젝트 버튼**: 그 프로젝트의 노선 색으로 테두리를 굵게 그리고, 버튼에 쓸 이름(네 글자까지 · 처음에는 프로젝트 이름 첫 낱말의 앞 세 글자)을 고칠 수 있어요. 누르면 가닥 창을 앞으로 가져오지 않고 그 프로젝트에서 가장 최근에 쓴 대화의 노선도가 떠요. 한 번 더 누르면 닫히고, ‘노선도’나 가닥 버튼으로 열면 다시 ‘지금 쓰는 대화’예요. 떠 있는 목록 창도 같은 프로젝트를 따라가요. 그 프로젝트의 대화를 목록에서 다 빼면 버튼도 빠져요.
- **편집 창**: 가닥 버튼 오른쪽 클릭 → ‘버튼 편집…’(메뉴 막대의 보기 → 떠 있는 버튼 편집…). 미리 보기 · 지금 버튼(↑ ↓ 빼기 · 이름 칸) · 더할 수 있는 기능 · 더할 수 있는 프로젝트 · 처음 모양으로. 바꾸면 바로 저장해요.
- **앱이 받는 방식**: 앱은 4초마다 묻는 `GET /float`의 `slots`를 보고, 달라졌으면 둘레 버튼을 다시 놓아요. 버튼 수가 줄면 화면 안쪽 가운데로 모여요(36도 간격).
- **길**: `GET /float`(+ `slots` · `?project=`) · `GET /float/slots` · `POST /float/slots {slots | reset}` · `GET /float/edit`.

## 27. 10/8 — ‘AI 연결’의 API 키 칸이 OpenAI · Gemini 키도 받게 (LLM API 키)

구현 담당이 정한 것이에요: **다른 사람들이 자기 LLM 키를 넣어 쓸 수 있게.** 전에는 Anthropic 키(`sk-ant-`)만 받아서, OpenAI나 Gemini 키를 넣으면 “API 키 모양이 아니에요”로 거절됐어요.

### 27-1. 무엇이 바뀌었나

| | 전 | 지금 |
|---|---|---|
| 칸의 이름 | API 키 (Anthropic) | **LLM API 키 (Anthropic · OpenAI · Gemini)** |
| 칸에 흐리게 적힌 글 | sk-ant-… | LLM API 키 넣기 |
| 받는 키 | Anthropic | Anthropic(`sk-ant-`) · OpenAI(`sk-`) · Google Gemini(`AIza` · `AQ.`) |
| 연결된 뒤의 상태 글 | 연결됨 · sk-ant-…끝 네 글자 | 연결됨 · **OpenAI** · sk-…끝 네 글자 (회사 이름이 보여요) |
| 맨 위 한 줄 | 지금은 API 키으로 정리해요 | 지금은 **OpenAI API 키로** 정리해요 (‘키으로’였던 조사도 고쳤어요) |
| 넣었을 때의 알림 | API 키를 키체인에 넣었어요. | **OpenAI** API 키를 키체인에 넣었어요. |
| 모양이 아닐 때 | API 키 모양이 아니에요. sk-ant-로 시작하는 키를 넣어 주세요. | API 키 모양이 아니에요. Anthropic · OpenAI · Gemini의 키를 넣어 주세요. |

- 칸은 그대로 **하나**예요. 회사를 고르는 단추는 없어요. 가닥이 키의 앞머리를 보고 알아봐요.
- 넣어 두는 키도 **하나**예요. 다른 회사 키로 바꾸려면 ‘키 지우기’를 누르고 새 키를 넣어요.
- Gemini 키가 들어 있으면 그 칸의 설명 끝에 한 문장이 더 붙어요: “Gemini 무료 키는 요금이 없는 대신, 보낸 글이 Google의 제품 개선에 쓰일 수 있어요.”
- 도움말(‘AI 연결’ 주제)과 설치 안내 PDF(1쪽 준비물 · 3쪽 AI 연결)의 글과 그림 둘(`ai-first.png` · `ai-done.png`)을 새 화면에 맞췄어요. PDF는 그대로 일곱 쪽이에요.

### 27-2. 어떻게 만들었나 (`backend/engines/`)

- **회사 알아보기** (`keys.py`): 키의 앞머리 → 회사. `sk-ant-`는 Anthropic, `sk-or-`(OpenRouter)는 받지 않음, 그 밖의 `sk-`는 OpenAI, `AIza` · `AQ.`는 Gemini. 모양은 앞머리까지만 봐요(길이 20~400자, 키체인 명령에 넣어도 되는 글자). 맞는 키인지는 그 회사가 답해요. **Gemini의 `AQ.`는 2026-05-28부터 Google AI Studio가 주는 새 키 모양이에요.** `AIza`만 받았다면 오늘 새로 만든 무료 키가 전부 거절됐을 거예요.
- **엔진 셋** — `anthropic_api`(있던 것 · 공식 SDK) · `openai_api` · `gemini_api`(새로 · SDK 없이 HTTP로). 넣어 둔 키의 회사에 따라 하나가 불려요. API 키 엔진은 어느 이름으로 골라 뒀어도(`GADAK_ENGINE=anthropic_api`, 화면에서 고른 것) 갖고 있는 키의 회사를 따라가요.
- **키는 그 회사로만** 가요. 엔진은 자기 회사 키일 때만 키를 받아요(`keys.get(회사)`). OpenAI 키가 들어 있는데 Anthropic 엔진이 불려도 그 키를 Anthropic으로 보내지 않아요. 새 키를 확인할 때도 그 회사에만 물어요.
- **OpenAI** (`openai_api.py`): Responses API(`POST /v1/responses`). 답의 형식은 구조화 출력(`text.format` · `strict`), 생각 단계는 `low`, 보관하지 않게 `store: false`. 모델은 GPT-6 Luna · GPT-6.1 Sol · GPT-6 Astra.
- **Gemini** (`gemini_api.py`): `generateContent`. 답의 형식은 `generationConfig.responseFormat.text`(`mimeType: APPLICATION_JSON` · `schema`). 키는 `x-goog-api-key` 머리로 보내요. 모델은 Gemini 3.5 Flash-Lite · 3.8 Flash · 3.1 Pro(미리 보기). Flash-Lite는 처음부터 가장 낮게 생각해서 그대로 두고, 나머지는 `thinkingLevel: LOW`.
- **보내는 길** (`rest.py`): 두 엔진이 같이 써요. Anthropic SDK가 쓰는 httpx2로 보내서 더 까는 것이 없어요(`requirements.txt`에 이름만 적었어요). 한도(429) · 서버 과부하(5xx) · 끊긴 연결은 서버가 말한 만큼(1분까지) 기다렸다 두 번까지 다시 보내요. 넣어 둔 돈을 다 썼거나(OpenAI) 하루 한도를 다 쓴 것(Gemini)은 기다려도 안 풀려서 바로 알려요. 답이 늦어서 끊긴 것은 다시 보내지 않아요(같은 요청에 돈이 또 나가요).
- **모델 이름**: `GADAK_ENGINE_MODEL`의 `haiku` · `sonnet` · `opus`를 ‘작은 것 · 중간 · 큰 것’으로 읽어 그 회사 모델로 옮겨요. 그래서 2단(`GADAK_CHECK_MODEL`) · 앞길 살피기(`GADAK_AHEAD_MODEL=sonnet`)의 설정을 고치지 않아도 돼요. 앞길 살피기의 생각 깊이(`GADAK_AHEAD_EFFORT`)도 두 엔진이 받아요.
- **키체인**: 자리 이름을 `anthropic-api-key`에서 `api-key`로 바꿨어요(키체인 접근 앱에 보이는 이름은 ‘가닥 · LLM API 키’). 예전 자리에 넣어 둔 Anthropic 키는 그대로 읽고, 새 키를 넣거나 지울 때 예전 자리도 같이 치워요.
- **환경 변수**: `GADAK_API_KEY`(어느 회사 키든)를 새로 봐요. 예전 이름 `ANTHROPIC_API_KEY`도 그대로 봐요. **`OPENAI_API_KEY` · `GEMINI_API_KEY`는 보지 않아요.** 다른 도구에 쓰려고 넣어 둔 사람이 많은 이름이라, 가닥에게 준 적 없는 키로 돈이 나갈 수 있어서요(알아서 고르는 차례에서 키가 ChatGPT 구독보다 먼저예요).
- **길**: `POST /engine/key` · `DELETE /engine/key` · `GET /engine`의 모양은 그대로예요. `key`와 `options`의 API 키 줄에 `company`(“OpenAI” 같은 회사 이름 · 없으면 null)가 더해졌고, `options`의 그 줄의 `name`은 갖고 있는 키의 엔진 이름이에요(키가 없으면 전처럼 `anthropic_api`).
- 같이 고친 것: 앞길 살피기가 엔진에 닿지 못했을 때의 글 “Claude에 닿지 못했어요”를 “정리하는 AI에 닿지 못했어요”로(ChatGPT 구독 · 다른 회사 키일 때도 Claude라고 나왔어요).

### 27-4. 확인한 것 · 못 한 것

확인한 것

- 테스트 309개 통과(3개 건너뜀). 새로 쓴 것 24개: 키의 회사 알아보기 · 예전 자리의 키 · 환경 변수, 보내는 길(기다렸다 다시 보내기), OpenAI · Gemini 엔진(보내는 모양 · 답 읽기 · 거절 · 잘림 · 오류 한 줄 · 새 키 확인), 엔진 고르기, 서버의 길.
- **가짜 키로 실제 서버에 대어 본 것** (돈이 들지 않아요)
  - 세 회사가 틀린 키를 거절하고, 가닥이 “API 키가 맞지 않아요. 키를 다시 넣어 주세요.”로 알리는 것. 가닥 창의 칸에 가짜 키를 쳐 넣고 ‘저장’을 진짜 클릭으로 눌러서 봤어요(OpenAI · Gemini의 예전 모양과 새 모양 · Anthropic).
  - **Gemini 서버가 가닥의 요청을 받아들이는 것.** Gemini는 키보다 요청의 칸 이름과 값을 먼저 검사해요. 분류 · 구간 나누기 · 놓친 일 · 앞길의 형식 넷을 작은 것 · 중간 · 큰 모델과 생각 깊이마다 보내서 “틀린 키”라는 답(= 모양은 통과)을 받았어요. 이때 **공식 문서의 예시가 틀린 것을 하나 찾았어요**: 문서는 `mimeType: "application/json"`이라고 적었는데 실제 서버는 그 값을 거절하고 `APPLICATION_JSON`만 받아요.
- **진짜 macOS 키체인**: 시험용 이름의 자리에 가짜 키 셋(OpenAI · Gemini 예전 모양 · 점이 든 새 모양)을 넣고 · 읽고 · 지웠어요. 예전 자리의 키를 읽는 것과, 새 키를 넣으면 예전 자리가 비는 것도요. 쓰던 키는 건드리지 않았어요.
- **화면**: 연결한 것이 없을 때 · OpenAI 키가 있을 때 · Gemini 키가 있을 때의 ‘AI 연결’ 창, ‘AI 없이 쓰기’ · ‘알아서 고르기’ · ‘이걸로 정리하기’의 알림 글, 도움말. 설치 안내 PDF의 1쪽 · 3쪽.
- **받아서 쓰는 앱과 디스크 이미지를 다시 만들었어요**(`python -m backend.macapp --dmg` · 사용 기록 서버 주소는 전처럼 넣지 않음). 묶인 앱의 사본을 저장소 밖에서 다른 포트로 켜고 가짜 키를 넣어, 앱 안의 새 엔진이 세 회사의 실제 서버에 닿아 “API 키가 맞지 않아요”를 받아 오는 것을 봤어요. 디스크 이미지 안의 설치 안내 PDF가 새로 찍은 것과 같은 것도요. 앱의 창을 띄워 눌러 보지는 않았어요(겉은 바뀌지 않았어요).

못 한 것

- **진짜 OpenAI · Gemini 키로 답을 받아 보는 것.** 구현 담당에게 키가 없어요. 그래서 아래는 공식 문서(10/8)대로 만들었을 뿐 실제로 본 적이 없어요: ① OpenAI가 요청을 받아들이는지(OpenAI는 키를 먼저 검사해서 가짜 키로는 요청 모양을 볼 수 없어요) ② 두 회사가 가닥의 답 형식(schema)을 받아들이는지 ③ 답을 읽는 것(쓴 토큰 · 거절 · 잘림) ④ 맞는 키가 ‘연결됨’으로 바뀌는 것 ⑤ 한도에 걸렸을 때 서버가 실제로 주는 답의 모양. **키가 있는 조원이나 써 볼 사람이 한 번 넣어 봐야 해요**: ‘AI 연결’에 키를 넣고, 대화 하나가 정리되는지 보면 돼요. 터미널로는 `./.venv/bin/python -m backend.engines --ping`.
- **OpenAI · Gemini 모델의 정리 품질.** 재지 않았어요. 키가 있으면 `python -m eval`로 Claude와 같은 대화에 대어 볼 수 있어요.
- Gemini의 새 키(`AQ.`)에 어떤 글자가 들어가는지는 실제 키를 보지 못했어요. 영문 · 숫자 · `-` · `_` · `.`를 받게 했어요. 다른 글자가 든 키가 있으면 “API 키 모양이 아니에요”로 거절돼요.
